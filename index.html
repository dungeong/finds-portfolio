메모리 부족 서버 장애 — 증상과 진단

512MB 인스턴스에서 API 응답이 느려지고 연결이 끊겼습니다. 애플리케이션 버그를 찾기 전에 호스트 자원 상태부터 확인했습니다.

관찰한 사실 운영

영역관찰 내용
API 응답요청 응답 지연, 연결 초기화(connection reset) 발생
메모리·디스크스왑 입출력이 심하고 I/O 대기가 높게 유지됨
Dockerdocker stop까지 지연되어, 바깥에 건 timeout이 종료 코드 124(시간 초과)로 끝남
앱 컨테이너종료 코드 137로 종료 — 프로세스가 SIGKILL로 끝났다는 의미

판단

스왑과 I/O 대기가 함께 높았고, 앱 요청뿐 아니라 Docker 관리 명령까지 느려졌습니다. 특정 API 로직이 아니라 호스트 전체가 메모리 부족으로 스왑에 의존하며 디스크 I/O가 포화된 상태로 판단했습니다. 따라서 코드 수정보다 메모리 용량 확보가 우선이라고 결론 내렸습니다.

단정하지 않은 것

불확실성

  • 종료 코드 137은 SIGKILL을 뜻할 뿐입니다. 커널 OOM Killer일 수도, 중지 시간 초과 뒤의 강제 종료일 수도 있습니다.
  • 컨테이너의 OOMKilled 값을 확인하지 않았으므로 “OOM 확정”으로 보지 않습니다. 미확인
  • 프로세스별 메모리 점유 분해 수치는 이 자료에 포함하지 않았습니다.

진단 순서에서 지킨 원칙

  • 관리 명령조차 느린 상태에서는 재시작을 반복하기 전에 데이터를 먼저 보호합니다.
  • 증상(지연·137)과 원인(메모리 압박)을 분리해 기록하고, 확인한 범위만 결론에 씁니다.
  • 운영 Compose·환경 파일이 서버에만 있다는 점을 고려해, 디스크를 통째로 옮길 수 있는 방법을 택합니다 → 다음 장.

CASE 02 · #54 / PR #59

게스트 선택 미션의 로그인 후 제출 실패 — 문제와 설계

완료 API의 검증을 완화하지 않은 이유

완료 기록 API는 당일 후보 여부·당일 중복 완료·이미지 소유권을 검사하는 인가 지점입니다. 여기서 후보 검사를 빼면 어떤 미션이든 완료할 수 있게 됩니다. 그래서 검증은 그대로 두고, 로그인 직후 선택한 미션을 오늘 후보로 연결하는 단계를 앞에 추가했습니다. 코드

세 가지 상태로 응답 코드

오늘 후보 상태처리
없음CONNECTED — 선택 미션을 1번으로, 나머지는 기존 발급 규칙(최근 48시간 노출 제외·가중치 선정)으로 최대 3개 발급
선택 미션 포함ALREADY_CANDIDATE — 기존 세트 그대로. 발급 후 비활성화된 미션도 이어서 수행 가능
선택 미션 미포함REJECTED_CANDIDATES_ALREADY_FIXED — 기존 세트를 바꾸지 않고 거부

세 결과 모두 HTTP 200입니다. success: true가 연결 성공을 뜻하지 않으므로 앱은 반드시 data.status로 분기해야 한다고 API 문서에 명시했습니다. 인증 실패·ID 형식 오류·존재하지 않거나 비활성인 미션은 별도 4xx로 응답합니다.

앱과 맞춘 호출 계약

  • 로그인 직후 홈 후보 발급보다 연결 API를 먼저 호출합니다. 홈 발급이 먼저 끝나면 다른 3개가 확정되어 연결이 거부될 수 있기 때문입니다.
  • 거부 상태에서는 기존 오늘 후보를 응답에 함께 내려주어, 앱이 홈 화면으로 자연스럽게 안내할 수 있게 했습니다.
  • 이 API가 증명하지 않는 것(게스트 화면에서 실제로 봤는지)을 문서에 따로 적었습니다 → 다음 장.

게스트 선택 미션 이어하기 — 동시성과 검증

홈 후보 발급과 같은 잠금으로 직렬화 코드

// 설명용 의사코드 — 직접 작성, 실제 서비스 코드 발췌 아님
연결요청(인증 사용자, 선택 미션):
  사용자 행 잠금               // SELECT … FOR UPDATE, 홈 후보 발급과 동일
  기준시각 = 시계.지금()        // 잠금 획득 후 한 번만 읽음
  오늘 = KST 날짜(기준시각)
  오늘후보 = 후보 조회(사용자, 오늘)
  만약 오늘후보가 있으면:
    선택 미션이 포함 → ALREADY_CANDIDATE        // 세트 유지
    포함되지 않음   → REJECTED_CANDIDATES_ALREADY_FIXED
  선택 미션 존재·활성 확인      // 실패 시 MISSION_001
  후보 = [선택 미션] + 기존 발급 규칙으로 고른 나머지
  저장 후 → CONNECTED

실제 서비스 코드는 팀의 비공개 저장소에 있으며 이 자료에는 포함하지 않았습니다.

  • 홈 후보 발급(issueUserCandidates)도 같은 사용자 행을 먼저 잠급니다. 두 요청이 동시에 와도 먼저 잠근 쪽만 오늘 후보 세트를 확정하고, 뒤의 요청은 확정된 세트를 보고 판정합니다.
  • 잠금을 얻은 뒤 시각을 한 번만 읽어, 한 요청 안에서 “오늘”이 바뀌지 않게 했습니다.
  • 나머지 슬롯은 기존 발급 로직을 그대로 재사용해 규칙이 두 갈래로 나뉘지 않게 했습니다.

현재 상태 — 백엔드 구현·배포 완료, 앱 연동 QA 미확인

배포 후 기존 앱으로 제출했을 때 MISSION_003이 다시 발생했습니다. 그 앱은 아직 연결 API를 호출하지 않는 버전이었습니다. 연결 API를 적용한 앱 버전의 종단 간 QA 완료는 마지막 확인 시점까지 보고받지 못했습니다. 미확인

CASE 03 · #50 / PR #51

기존 기록을 보존한 최종 미션 콘텐츠 전환

최종 기획 콘텐츠로 교체하면서, 이미 쌓인 후보·완료 기록이 가리키는 미션 ID를 하나도 지우거나 다른 미션으로 재사용하지 않았습니다.

왜 삭제·재사용을 하지 않았나

mission_candidates와 mission_records가 미션 ID를 참조합니다. 삭제하면 FK에 막히거나 기록이 끊기고, ID를 다른 미션에 재사용하면 과거 기록이 전혀 다른 미션을 가리키게 됩니다. 그래서 갱신·비활성화·신규 추가 세 가지만 사용했습니다.

마이그레이션 설계 코드

  • V13 — reference_image_key를 nullable로 추가하고 기존 reference_image_url은 그대로 둠. 배포 중인 구버전 앱 인스턴스는 새 컬럼을 매핑하지 않아 영향이 없음.
  • V14 — 활성 미션 CHECK 제약을 “URL 또는 key”로 바꾼 뒤 콘텐츠 반영. 신규 6개는 key만 가짐. 테스트용 H2와 같이 동작하도록 ON CONFLICT 대신 NOT EXISTS 사용.

응답 시 이미지 해석 규칙 코드

  • MissionReferenceImageResolver 한곳에서 처리: key가 있으면 Presigned URL을 발급하고, 없을 때만 기존 URL을 반환합니다. 두 값을 섞지 않습니다.
  • 서명이 실패하면 예외를 그대로 전파합니다. 더미 URL로 감추지 않습니다.

비활성 미션 정책 코드

  • 이미 발급된 본인의 당일 후보는 비활성화 후에도 재조회·상세·완료 허용
  • 신규 후보 선정과 게스트 후보에서는 제외, 다른 사용자의 상세·완료는 거부

운영 적용 확인 운영

A가이드 이미지 403 진단

#50 배포 후 가이드 이미지의 Presigned URL은 정상 발급되는데 다운로드가 403이었습니다. 운영

  • 판단: Presigned URL은 SDK가 로컬에서 서명만 계산하므로 생성 성공이 권한을 보장하지 않습니다. 권한은 다운로드 시점에 서명 주체 기준으로 평가됩니다.
  • 원인: 실제 응답을 조사한 결과, 앱 IAM 주체에 가이드 이미지 접두사의 s3:GetObject 허용이 없었습니다.
  • 조치: 해당 접두사에 한정한 읽기 권한만 추가했습니다. 버킷 공개는 하지 않았습니다.
  • 확인: 이미지 1건 HTTP 200, image/jpeg 다운로드

미확인 24개 전체 이미지 다운로드는 검증하지 않았습니다.

B회고 300자 — 계약과 DB 제약 일치 (#60)

기획은 세 항목 각 300자인데, 서버는 한 줄 평 50자·잘한 점/어려운 점 100자로 제한하고 있었습니다.

  • 조치: 요청 DTO @Size(max = 300), 엔티티 length = 300, 신규 V15로 VARCHAR(300)을 함께 맞춤. 적용된 기존 마이그레이션은 수정하지 않음 코드
  • 검증: 컨트롤러 테스트 26건(299·300자 허용, 301자 거부). V14 데이터가 있는 DB에 V15 적용·기존 데이터 보존과 신규 DB 전체 마이그레이션을 PostgreSQL 테스트 11건으로 확인 운영
  • 배포: 918b5c2, ping 200, V15 성공, 세 컬럼 길이 300 확인 운영

전체 337건 실행은 Docker 없이 262건 성공·75건 스킵이었으므로 “전체 통과”로 보지 않습니다. 길이는 String.length() 기준이라 이모지가 섞이면 체감 글자 수와 다를 수 있습니다. 실제 앱 300자 제출 QA는 미확인

COLLABORATION

KPI 정의를 실제 계측·API 요구사항으로 구체화

PM의 KPI·이벤트 문서를 실제 앱 화면 흐름과 서버 API 처리 단위에 맞춰 검토했습니다. 아래는 설계 검토와 협의 결과이며, 수집·분석은 아직 시작 전입니다.

1발견한 문제

  • 사진 업로드 실패가 완료 실패 이벤트에서 빠져 있음
  • 오류 유형이 앱이 실제로 구분할 수 없는 기준으로 정의됨
  • 노출과 선택의 집계 단위가 달라 전환율이 왜곡될 수 있음
  • 미션 시작 시점이 버튼 클릭 기준이라 실제 수행과 어긋남
  • 게스트 이어하기는 선택 없이 시작부터 기록될 수 있음
  • 회고 작성량 구간이 300자 정책과 맞지 않음

2제안한 기준

  • 업로드 실패도 완료 실패에 포함
  • 오류 유형은 업로드·최종 제출·네트워크로 나누고, 재시도는 각각 별도 시도로 집계
  • 노출·선택 모두 앱 인스턴스·미션·KST 날짜 기준으로 각각 중복 제거
  • mission_start = 실제 수행 화면 진입
  • mission_complete = 최종 저장 API 성공 응답 이후
  • 게스트 이어하기의 select 누락을 분석 예외로 명시
  • 작성량 구간 갱신, 회고 원문은 전송하지 않음

3PM과 정리된 방향

  • 핵심 퍼널: mission_select → mission_start → mission_complete
  • 첫 완료일 D0를 제외한 KST D1~D7 추가 완료 집계
  • D7 관찰이 끝난 앱 인스턴스만 분모, QA 대상 제외
  • MVP 분석 단위는 회원 계정이 아닌 앱 인스턴스
  • D1~D7 집계·태그 매핑은 BigQuery 기준으로 진행 예정
  • 필터 적용 이벤트는 MVP에서 제외

4남은 구현

  • 앱 이벤트 구현 — 앱 개발자 담당
  • 분석 선택 동의의 저장·조회·변경·철회와 로그인 상태에 따른 수집 제어 — 앱 개발자와 연동 범위 정리
  • 후속 이슈 #62 — 기존 코드 조사, 설계 보완, PM 정책 협의까지 진행(10.02 기준). 구현·배포 완료 보고 없음 미확인
  • Daily Export 연결과 실제 적재 확인 — 후속 작업 미확인

대표 판단 — 노출과 선택은 같은 키로 세야 비교할 수 있다

노출을 화면이 그려질 때마다 세고 선택은 한 번만 센다면, 같은 사람이 홈을 여러 번 열수록 선택률이 실제보다 낮아집니다. 그래서 두 이벤트 모두 앱 인스턴스·미션·KST 날짜 조합으로 각각 중복 제거하자고 제안했고, 날짜 경계는 서버의 당일 후보 기준(KST)과 맞췄습니다.

기여 범위 — KPI·정책 문서 작성과 최종 기획 결정은 PM과의 공동 작업이고, 앱 이벤트 구현은 앱 개발자 담당입니다. 저는 기술적 모순·누락 검토와 서버 계약·연동 범위 조율에 기여했습니다.

지표 개선 수치나 분석 성과는 아직 없습니다. 근거는 비공개 팀 문서·대화이므로 원본 화면 대신 익명화한 요약으로 정리했습니다.
