# 회고 입력 길이 300자 통일

> 기획과 서버의 입력 제한이 달라 300자 회고 제출이 실패할 수 있었습니다.
> 입력 검증만 완화하지 않고 DTO·엔티티·DB 제약을 함께 맞추고, 기존 데이터가 있는 DB의 업그레이드 경로까지 검증했습니다.

## 1. 문제

| 항목 | 기획 | 기존 서버 제한 |
| --- | --- | --- |
| 한 줄 평 | 최대 300자 | 50자 |
| 잘한 점 | 최대 300자 | 100자 |
| 어려운 점 | 최대 300자 | 100자 |

사용자에게서 300자 제출 실패가 보고됐습니다. 다만 당시 조회한 운영 로그로 **그 실패 요청의 원인을 직접 추적하지는 못했습니다.**
확인한 것은 코드의 제한 불일치와, 아래 테스트로 검증한 변경 후 동작입니다.

## 2. 선택한 해결책과 이유

입력 검증(DTO)만 늘리면 요청은 통과해도 DB 컬럼 길이에서 다시 실패합니다. 그래서 세 계층을 함께 바꿨습니다.

| 계층 | 변경 |
| --- | --- |
| 요청 DTO | 세 필드를 `@Size(max = 300)`으로 통일 |
| JPA 엔티티 | 세 컬럼의 `length = 300`을 일치 |
| DB | 신규 Flyway 마이그레이션 V15로 세 컬럼을 `VARCHAR(300)`으로 확장 |

- **이미 적용된 기존 마이그레이션은 수정하지 않았습니다.** 운영 DB에 적용된 스크립트를 고치면 체크섬이 달라져 Flyway 검증이 실패하고, 이력과 실제 스키마가 어긋납니다.
- 기존 값은 모두 50/100자 이내라 확장만으로 충분했고, 데이터 변환이나 잘라내기는 필요 없었습니다.
- 필수·선택 입력 정책, 응답 필드, 기존 오류 계약은 바꾸지 않았습니다.

## 3. 검증

검증은 실행 시점과 범위가 서로 다르므로 나누어 적습니다. 건수를 합산하지 않습니다.

| 실행 | 결과 | 의미 |
| --- | --- | --- |
| 컨트롤러 테스트 | 26건 통과 | 299·300자 허용, 301자 거부 등 경계값 |
| 전체 스위트 (Docker 미실행) | 337건 중 성공 262, **스킵 75** | Testcontainers 기반 테스트가 스킵됨. **"전체 통과"로 보지 않음** |
| Docker 실행 후 관련 PostgreSQL 테스트 2개 클래스 | 11건 성공, 실패·오류·스킵 0 | 아래 업그레이드 경로 검증 |

PostgreSQL 테스트로 확인한 내용:

- V14까지의 데이터가 있는 DB에 V15를 적용해도 기존 데이터가 보존됨
- 세 필드에 300자를 동시에 저장하고 조회 가능
- 빈 DB에서 전체 마이그레이션이 처음부터 적용됨

운영 확인(운영 보고):

| 항목 | 결과 |
| --- | --- |
| 배포 이미지 | `918b5c2` 커밋 기반 |
| `GET /api/v1/ping` | HTTP 200 |
| Flyway V15 | `success = true` |
| `information_schema` 조회 | 세 컬럼 모두 길이 300 |

## 4. 한계

- 길이는 기존과 같은 Java `String.length()` 기준(UTF-16 코드 단위)입니다. 이모지처럼 두 단위를 쓰는 문자가 섞이면 **사용자가 보는 글자 수와 다를 수 있습니다.**
- 배포 후 실제 앱에서 300자 회고 제출이 성공했다는 보고는 마지막 확인 기준 없습니다.
- 사용자가 보고한 실패 요청 자체의 원인은 로그로 직접 추적하지 못했습니다. 요청 단위 추적 로그를 넓히는 것을 다음 과제로 남겼습니다.
