# 운영 장애 진단과 서버 이전

> 메모리가 부족한 서버에서 응답 지연과 연결 끊김이 발생한 사례입니다.
> 원인을 단정하기보다 데이터 보호를 먼저 하고, 확인한 범위만 결론으로 남겼습니다.

## 1. 문제

512MB 인스턴스에서 실행 중인 API 서버에서 다음 증상이 함께 나타났습니다.

| 영역 | 관찰한 사실 |
| --- | --- |
| API 응답 | 요청 응답 지연, 연결 초기화(connection reset) |
| 메모리·디스크 | 스왑 입출력이 심하고 I/O 대기가 높게 유지됨 |
| Docker | `docker stop`까지 지연되어, 바깥에 건 `timeout` 명령이 종료 코드 124(시간 초과)로 끝남 |
| 앱 컨테이너 | 종료 코드 137로 종료 |

## 2. 근거와 판단

**판단:** 앱 요청뿐 아니라 Docker 관리 명령까지 느렸고, 스왑과 I/O 대기가 함께 높았습니다.
그래서 특정 API 로직의 문제가 아니라 **호스트 전체가 메모리 부족으로 스왑에 의존하며 디스크 I/O가 포화된 상태**로 판단했습니다.
코드 수정보다 메모리 용량 확보를 우선했습니다.

**단정하지 않은 것:**

- 종료 코드 137은 `128 + 9`, 즉 프로세스가 SIGKILL로 끝났다는 뜻입니다.
  커널 OOM Killer일 수도 있고, 중지 시간 초과 뒤의 강제 종료일 수도 있습니다.
- 컨테이너 상태의 `OOMKilled` 값은 확인하지 않았습니다. 그래서 이 사례를 **"OOM 확정"으로 기록하지 않습니다.**
- 프로세스별 메모리 점유를 나눈 수치는 남기지 않았습니다.

## 3. 선택한 해결책과 이유

| 순서 | 조치 | 이유 |
| --- | --- | --- |
| 1 | 메모리·스왑·I/O·컨테이너 종료 상태 진단 | 증상과 원인을 나눠 기록하기 위해 |
| 2 | `pg_dump`로 DB 논리 백업, `pg_restore --list`로 아카이브 목차 확인 | 관리 명령조차 느린 상태에서 인스턴스 작업이 실패하면 DB를 잃을 수 있어, 복구 수단부터 확보 |
| 3 | 스냅샷 기반으로 2GB 인스턴스 이전 | 운영 Compose·환경 파일이 서버에만 있어, 새 서버를 손으로 다시 구성하면 설정 누락 위험이 큼 |
| 4 | JVM 메모리 옵션 조정 | 메모리를 먼저 늘린 뒤 그 범위 안에서 앱 프로세스 상한을 다시 맞춤 |
| 5 | 고정 IP 연결, 방화벽 규칙 설정 | 새 인스턴스로 기존 접속 경로를 옮기기 위해 |
| 6 | 앱 재기동, 응답 확인 | 아래 검증 |

```mermaid
flowchart LR
    A["증상 확인<br/>지연·스왑·I/O 대기"] --> B["DB 백업<br/>pg_dump"]
    B --> C["목차 확인<br/>pg_restore --list"]
    C --> D["스냅샷으로<br/>2GB 인스턴스 이전"]
    D --> E["JVM 메모리 조정<br/>고정 IP·방화벽"]
    E --> F["재기동·응답 확인"]
```

## 4. 검증

이전 후 확인한 값입니다(운영 기록).

| 항목 | 값 |
| --- | --- |
| `free -h` 전체 메모리 | 약 1.9GiB |
| `free -h` 사용 가능 메모리 | 약 1.1GiB |
| `vmstat` 후속 샘플 swap in/out | 0 |
| `GET /api/v1/ping` | HTTP 200 |

## 5. 한계

- 위 값은 **관찰 시점**의 운영 확인입니다. 부하 테스트나 장기 안정성 검증이 아닙니다.
- 백업은 `pg_dump` 성공과 목차 확인까지입니다. **별도 DB로 실제 복원하는 시험은 하지 않았습니다.**
- 이전 전후의 응답 속도 개선율 같은 정량 비교는 측정하지 않았습니다.
- 장애 원인이 OOM인지는 확정하지 않았습니다.
